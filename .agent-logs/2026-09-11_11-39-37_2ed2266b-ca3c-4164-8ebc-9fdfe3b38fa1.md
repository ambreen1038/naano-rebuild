## Supabase — schema design, senior-dev reasoning

Five tables, matching the brand-portal-first scope we agreed on:

| Table | Purpose |
|---|---|
| `profiles` | One row per brand/company user, 1:1 with `auth.users`. Auto-created by a trigger on signup — the app never has to handle "user exists but no profile yet." |
| `creators` | Seeded marketplace data (name, vertical, followers, price/post). **Not a login-able role** — matches our decision to treat creators as data, not a built portal. |
| `campaigns` | A brand's briefs: objective, key messages, creator guidelines, target vertical, budget, and a `landing_url` (where the tracked link ultimately sends traffic — e.g. your signup page). |
| `bookings` | The campaign × creator pipeline: `draft → scheduled → live → completed`, plus `contract_status` / `invoice_status` / `payout_status` for the mocked payments view, and a unique `tracking_slug` per booking. |
| `click_events` | Real attribution — one row per click, written only by the server-side `/r/[slug]` redirect route, never by the browser directly. |

Design calls worth flagging:
- **RLS everywhere.** A brand can only ever see/edit its own `campaigns` and `bookings` (checked via `auth.uid()`), enforced at the database layer, not just in app code — so a bug in a page component can't leak another company's data.
- **`creators` requires login to browse**, matching the real product (self-serve is free, but you sign up to see the marketplace).
- **`click_events` has no insert policy for clients at all** — only a server route using the service-role key can write to it, since the clicks come from anonymous LinkedIn visitors, not signed-in brands.
- **`fit_score` is stored per booking**, not computed live — a snapshot of "why we suggested this creator" at the time of booking, so it doesn't silently change later.
